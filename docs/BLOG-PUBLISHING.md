# قرارداد تحویل مقاله به مجلهٔ هما

این راهنما با Sync فعال سرور در 2026-11-12 تطبیق داده شده است؛ هدف، تولید محتوا برای همان سیستم موجود است، نه ساخت بلاگ، Build یا سرویس جدید.

## مقصد دقیق

- Repository: `Powerostad/HomaFrontend`
- شاخهٔ آمادهٔ انتشار: `content/blog-<slug>-YYYYMMDD`
- نمونهٔ این مقاله: `content/blog-before-after-living-room-20261111`
- slug: انگلیسی، حروف کوچک، عدد و خط تیره؛ یکتا و پس از انتشار ثابت.

```text
public/
  blog/
    <slug>/
      index.html
    images/
      <slug>/
        cover.jpg
        before.jpg
        after.jpg
docs/
  BLOG-PUBLISHING.md
```

نمونهٔ فعلی:

```text
public/blog/living-room-before-after/index.html
public/blog/images/living-room-before-after/before-1080.jpg
public/blog/images/living-room-before-after/after-735.jpg
```

لینک نهایی: `https://myhoma.ir/blog/<slug>`.

**فایل `content/blog/review/.../article.html` ورودی انتشار نیست.** یک PR یا فایل بریف approved نیز به‌تنهایی مقاله را وارد سیستم نمی‌کند. برای انتشار، HTML نهایی باید دقیقاً در مسیر `public/blog/<slug>/index.html` و در شاخهٔ `content/blog-*` وجود داشته باشد. Sync فعال همچنین `dev` و شاخه‌های اصلاحی `fix/blog-*` را می‌خواند؛ برای مطالب تازه از شاخهٔ content اختصاصی استفاده کن، نه تغییر کد برنامه در dev. قواعد بالا به هر سه منبع تحت پایش مربوط‌اند.

## تفاوت پیش‌نویس و انتشار

برای پیش‌نویس، از شاخهٔ `draft/blog-<slug>-YYYYMMDD` یا مسیر `content/blog/review/<slug>/article.html` استفاده کن. فقط پس از درخواست انتشار کاربر، نسخهٔ نهایی را به مسیر عمومیِ شاخهٔ `content/blog-*` منتقل/کپی کن.

**هشدار اجرایی مهم:** در پیاده‌سازی فعلی، Draft بودن PR، متای noindex و status موجود در JSON مانع انتشار توسط Sync نیستند. بنابراین HTML آزمایشی را در مسیر عمومیِ شاخهٔ تحت پایش نگذار. این توضیح رفتار موجود است، نه یک Gate تازه.

شاخهٔ محتوایی و تصاویر آن را پس از انتشار یا Merge حذف نکن؛ به‌روزرسانی مطلب نیز از همان منبع خوانده می‌شود. یک slug را هم‌زمان در چند شاخه با نسخه‌های متفاوت تولید نکن.

## قرارداد HTML

یک سند UTF-8 شامل `html lang="fa" dir="rtl"`، title، meta description، یک H1 و متن کامل در main یا article تحویل بده. H1 حداکثر 200 کاراکتر و meta description حداکثر 400 کاراکتر؛ برای نمایش سئو عنوان کوتاه و توضیح تقریباً 150 تا 170 کاراکتری انتخاب کن. canonical باید HTTPS روی myhoma.ir و دقیقاً مربوط به همان slug باشد.

```html
<!doctype html>
<html lang="fa" dir="rtl">
<head>
  <meta charset="utf-8">
  <title>عنوان کوتاه و مشخص مقاله | هما</title>
  <meta name="description" content="پاسخ و فایدهٔ مشخص این مقاله برای خواننده">
  <meta name="robots" content="index,follow">
  <link rel="canonical" href="https://myhoma.ir/blog/example-slug">
  <meta property="og:image" content="https://myhoma.ir/blog/images/example-slug/cover.jpg">
</head>
<body>
  <main>
    <h1>عنوان مقاله</h1>
    <article>
      <p>پاسخ مستقیم و متن کامل مقاله؛ نمونهٔ خالی برای انتشار مناسب نیست.</p>
      <figure>
        <img src="/blog/images/example-slug/cover.jpg" alt="توضیح دقیق تصویر" width="1080" height="720">
        <figcaption>توضیح تصویر و مفهومی‌بودن آن، در صورت لزوم.</figcaption>
      </figure>
      <h2>راهنمای تصمیم‌گیری</h2>
      <p>توضیح کاربردی، متناسب با سؤال اصلی مقاله.</p>
      <a href="/studio/upload">بررسی فضای من در هما</a>
    </article>
  </main>
</body>
</html>
```

example-slug و متن نمونه را با مقالهٔ واقعی جایگزین کن. ساختار صفحه و تایپوگرافی را renderer فعلی سایت اعمال می‌کند. برای مفهوم مقاله به CSS اختصاصی، JS، iframe، فرم یا دکمهٔ سفارشی تکیه نکن؛ Sync این‌ها و class/styleها را حذف می‌کند. متن، تیتر، تصویر با alt و ابعاد، figcaption، جدول، فهرست و لینک معمولی مناسب‌اند. اطلاعات مهم را داخل header/nav/footer نگذار؛ این بخش‌ها از متن واردشده حذف می‌شوند.

در نسخهٔ نهایی عبارت «پیش‌نویس» و noindex نباشد. متن تأییدشده را بی‌دلیل کوتاه یا بازنویسی نکن. تاریخ اجرای واقعی، نتیجهٔ واقعی پروژه، آمار Search Console، هزینه یا مجوز تصویر را جعل نکن. زمان واقعی انتشار را CMS هنگام واردکردن مقاله ثبت می‌کند؛ تاریخ تهیهٔ Draft را به‌عنوان datePublished قطعی نساز. JSON-LD نهایی صفحهٔ زنده از دادهٔ مقالهٔ CMS تولید می‌شود و باید همان‌جا بررسی شود.

## تصاویر

- فایل واقعی JPEG، PNG یا WebP در همان شاخه و زیر `public/blog/images/<slug>/` باشد؛ حداکثر 3 MB برای هر تصویر. HTML حداکثر 2 MB.
- آدرس src در HTML، `/blog/images/<slug>/file.jpg` یا معادل کامل آن روی myhoma.ir باشد. لینک تصویر از دامنهٔ خارجی واردکننده را دچار خطا می‌کند.
- src و og:image هر دو باید به فایلی موجود در همان Git tree اشاره کنند. SVG حاوی JPEG، base64 بزرگ، فایل روی کامپیوتر شخصی و لینک موقت تحویل نده.
- alt، ابعاد واقعی و توضیح «کانسپت/بازطراحی مفهومی» در موارد لازم ثبت شوند. تصویر را به‌عنوان پروژهٔ اجرایی واقعی معرفی نکن مگر شواهدش موجود باشد.
- Sync تصاویر مرجع را به storage سایت منتقل و آدرس را به `/api/blog/assets/<hash>.<ext>/` تبدیل می‌کند. نبودن فایل خام در `/blog/images/...` روی هاست به‌تنهایی نشانهٔ شکست نیست؛ آدرس تصویر در **خروجی واقعی مقاله** را آزمایش کن.
- srcset و picture در sanitizer فعلی حفظ نمی‌شوند. نسخهٔ اصلی src باید به‌تنهایی خوانا و کم‌حجم باشد؛ وجود thumbnailها در Git، پشتیبانی responsive در CMS را تضمین نمی‌کند.

## انتشار و زمان‌بندی

مسیر موجود: GitHub branch → Sync بلاگ → دیتابیس مقالات + تصاویر ذخیره‌شده → Blog API → renderer فعلی سایت.

برای مقالهٔ تازه، Build استودیو، تغییر backend، ساخت اپ جدید، ادغام PRهای قدیمی یا تغییر رتبه‌بندی محصول لازم نیست. زمان‌بندی فعلی Sync هر 48 ساعت است. برای انتشار فوری، اپراتور می‌تواند فقط worker موجود blog-sync را دوباره اجرا کند؛ چرخهٔ اول Sync در شروع اجرا می‌شود. بازهٔ 48ساعته را تغییر نده و کل استودیو را برای انتشار مقاله Restart نکن. اگر دسترسی اجرای Sync نداری، «در صف Sync» گزارش کن؛ انتشار موفق ادعا نکن.

## کنترل قبل و بعد

1. پیش از ورود به مسیر عمومی، متن و تصاویر نهایی، canonical و لینک‌های داخلی را بررسی کن. از ورودی قبلی و مقالهٔ موجودِ همان slug بکاپ بگیر. نیازی به کپی دیتابیس خصوصی محصولات نیست.
2. قبل از Push، با parser فعال `apps/blog/github_content.py::parse_article` آزمایش کن و موجودبودن تصاویر و ابعاد/فرمت‌شان را بررسی کن. تست Draft به‌تنهایی تست نسخهٔ انتشار نیست.
3. پس از Push و اجرای Sync، وجود مقاله در `/api/blog/posts/<slug>/` و فهرست مقالات را تأیید کن.
4. HTML نهایی برای انسان و خزنده باید H1، canonical صحیح، robots قابل ایندکس، تاریخ واقعی و structured data معتبر داشته باشد. تصویر نهایی باید HTTP 200، نوع MIME صحیح و alt داشته باشد.
5. sitemap، لینک‌های داخلی و CTA استودیو را آزمایش کن. HTTP 200 یک SPA به‌تنهایی تأیید عملکرد مقصد نیست.
6. فقط پس از مشاهدهٔ نتیجهٔ زنده بگو «منتشر شد». یک commit، PR سبز، Merge یا status=approved به معنی انتشار نیست. در صورت خطا، مرحله و پاسخ واقعی را گزارش کن؛ مقاله را خودکار در چند مسیر متفاوت تکرار نکن.

## متن کوتاه برای تحویل به ایجنت تولیدکننده

«برای مجلهٔ هما در Powerostad/HomaFrontend مقاله تولید کن. پیش‌نویس خارج از مسیر عمومی باشد. پس از درخواست انتشار، HTML نهایی را در شاخهٔ content/blog-<slug>-YYYYMMDD و مسیر public/blog/<slug>/index.html بگذار. تصاویر واقعی و کم‌حجم در public/blog/images/<slug>/ باشند و src/og:image به همین فایل‌ها اشاره کنند. برای نمایش به JS یا CSS اختصاصی تکیه نکن. محتوای اصلی، alt، canonical، CTA و افشای کانسپت‌بودن تصویر حفظ شوند. تاریخ یا آمار نساز. ساختار backend/استودیو و تنظیم 48ساعتهٔ Sync را تغییر نده. پس از Sync، API، صفحه، تصویر و sitemap زنده را بررسی کن؛ تا آن زمان فقط آمادهٔ انتشار/در صف گزارش بده. جزئیات کامل در docs/BLOG-PUBLISHING.md است.»
